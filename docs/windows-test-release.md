# Windows 테스트판

이 패키지는 Yee의 사용자별 설치·실행·업데이트 수리·제거를 확인하기 위한 테스트판이다.
공개 정식 배포판이나 서명된 설치 파일로 취급하지 않는다. 브라우저 앱의 자동 업데이트는
아직 제공하지 않는다. 광고 필터의 자동 갱신은 별도로 동작한다.

## 설치와 데이터

함께 제공된 `Yee-버전-windows-아키텍처-test-unsigned.exe`를 실행한다.
관리자 권한이 없는 사용자별 설치를 대상으로 하며 시스템 전체 설치는 지원하지 않는다.

- 앱: `%LOCALAPPDATA%\Yee\Application`
- 설정·북마크·방문 기록: `%LOCALAPPDATA%\Yee\User Data`
- 시작 메뉴와 Windows 앱 목록: Yee

기존 Chrome·Chromium의 설치·프로필을 자동으로 가져오거나 변경하지 않는다.
Windows의 실행 파일 검색 등록도 `Yee.exe`라는 전용 키를 사용한다. 내부 실행 파일 이름은
`chrome.exe`이며, 다른 브라우저의 공유 `chrome.exe` 등록을 덮거나 삭제하지 않는다.
개발 중 사용한 Chromium 경로의 프로필도 이전하지 않는다. 수동으로 폴더를 덮어쓰지 않는다.
새 테스트판은 Yee를 정상 종료한 뒤 설치 파일을 실행해 적용한다. 별도 제거는 필요 없다.

| 설치 파일과 기존 설치 비교 | 처리 |
| --- | --- |
| 새 버전 | 기존 설치를 업데이트하고 프로필·북마크·설정을 유지 |
| 같은 버전 | 현재 설치 수리·데이터 유지 |
| 과거 버전 | 새 설치를 덮어쓰지 않고 거부 |

업데이트 검사는 기존 고정 링크의 실행 대상·아이콘 경로·앱 식별자가 같은 버전
재설치 뒤에도 유지되는지 비교한다. 바로가기 단위 검사는 고정 기능을 끄고
사용자 레지스트리를 임시 영역으로 분리하며, 실제 작업 표시줄의 고정·해제 API를
호출하지 않는다. 임시 검사 실행 파일이 사용자의 Yee 고정 항목을 대체하지 않아야 한다.

설치 검수에서는 그룹을 만든 상태로 정상 종료한 뒤 같은 버전을 재설치하고,
기존 작업 표시줄 아이콘으로 다시 여는 흐름도 함께 확인한다. 고정 대상·아이콘
경로·앱 식별자와 Windows가 읽은 아이콘 이미지, 그룹의 이름·색상·접힘·탭 구성을
재설치 전후로 비교한다. 검증용 탭만 정리하고 기존 사용자 그룹과 설정은 보존한다.

예를 들어 `153.0.8005.0` 설치 위에서 `153.0.8005.1` 설치 파일을 실행하면 새 버전으로
교체한다. 앱을 실행할 때 인터넷에서 설치 파일을 찾는 자동 업데이트는 아직 제공하지 않는다.

Windows 앱 목록에서 Yee를 선택해 제거한다. 기본 제거는 사용자 데이터를 보존한다.
제거 화면에서 데이터 삭제를 선택하면 Yee의 사용자 데이터도 삭제된다.

## 서명과 고지

현재 설치 파일은 서명하지 않았다. Windows가 확인되지 않은 게시자 경고를 표시하거나
실행을 제한할 수 있다. 조직의 보안 정책을 해제하지 말고 관리자에게 배포 방식을 확인한다.
정식 배포 전에는 게시자 서명·브라우저 보안 업데이트·깨끗한 별도 PC 검증이 필요하다.

패키지의 `release.json`에는 제품 버전·엔진 원본 버전(`chromium_version`)·원본 커밋·작업 트리 변경 여부·설치 파일의 SHA-256과
포함한 광고 차단 자료의 hash가 기록된다. 개발 중 변경된 소스가 포함됐으면
`working_tree_dirty`가 `true`다. 재현 가능한 공식 릴리즈를 주장하지 않는다.

설치 폴더의 버전 하위 폴더에는 `YeeContentBlockingNotices.txt`,
`YeeContentBlockingSources.tar.xz`, `YeeCommunityFilterNotices.txt`,
`YeeCommunityFilterSources.tar.xz`가 들어 있다. 외부 코드·목록·리소스의 고지와
해당 원본 소스를 이 파일에서 확인할 수 있다. Chromium 고지는 앱의 `chrome://credits`에서도
확인한다. 외부 배포 전의 전체 라이선스·개인정보 안내 검토는 별도 작업이다.

## 개발 도구와 확장 경계

`tools/dev/package-windows.ps1`이 기존 Chromium `mini_installer`를 빌드하고
`.local-build/releases/`에 설치 파일·메타데이터·이 안내를 만든다. 개발용 component 빌드도
Chromium의 runtime dependency 목록에 따라 DLL을 함께 묶는다. 정적 빌드도 같은 진입점을 쓴다.

`node tools/dev/test-windows-installer.mjs PACKAGE_DIRECTORY`는 기존 Yee 설치나 데이터가
없을 때만 시작한다. 실제 설치·기본 프로필·수리·제거 후 데이터 보존·재설치·시험 데이터까지
제거를 검사하고 진단 자료를 `.local-build/windows-install-test-*`에 남긴다.
검증 중 생성한 프로필만 삭제 대상으로 삼는다. 모든 Yee를 정상 종료한 뒤 실행한다.
기존 설치의 업데이트 검증은
`node tools/dev/test-windows-installer.mjs NEW_PACKAGE --upgrade-existing OLD_PACKAGE`를 쓴다.
정상 Yee 작업 표시줄 고정 항목이 이미 있어야 하며, 대상 파일·아이콘 경로·앱
식별자를 확인한 뒤 시작한다. 고정 항목이 없거나 대상이 잘못됐으면 검증을 중단한다.
구버전이 실제 설치됐는지 확인한 뒤 정상 실행·새 버전 업데이트·웹 저장 데이터와 기존
북마크·시작·홈·Yee 설정 보존·구버전 역설치 거부·같은 버전 수리·설치본 광고 차단을
검사한다. 이 모드는 기존 설치·프로필을 삭제하지 않는다. 검증을 위해 로컬 페이지를 열며
방문 기록은 남을 수 있다. 원래 설치와 일치하는 구버전 패키지도 함께 보관한다.
별도 시험 프로필에는 홈·시작 설정·광고 차단 예외를 넣고 구버전의 실제 북마크 API로
북마크를 만든다. 업데이트 뒤 같은 API와 저장 파일로 보존을 확인한다. 이 시험 데이터는
진단 폴더에만 만들고 실제 사용자 설정에는 넣지 않는다.
설치·수리 직후와 마지막 제거 후에 기존 Chrome·Chromium 등록·기본 브라우저·공유
실행 파일 키·과거 확장자 및 RLZ 데이터의 hash도 비교한다. native registry override
테스트는 타사 등록과 다른 실행 경로를 가리키는 Yee 이름의 키도 보존하는지 확인한다.
설치된 실행 파일에서도 Windows HTTP rendering fixture로 요청·프레임·CSS·scriptlet의
차단·해제·사이트 예외·정상 콘텐츠 복구를 검사한다. 이 fixture의 프로필은 일반 설치
프로필과 별도로 만든다. 외부 Chromium checkout을 쓰면 기존 빌드 도구와 동일하게
`YEE_CHROMIUM_ROOT`를 지정한다.

제품의 영속 식별자는 `branding/identity.json`, 표시 이름·로고는 `branding/brand.json`이
소유한다. `tools/overlay/product_identity.py`가 검증된 식별자를 native 빌드 입력으로 생성하고
기존 브랜딩 overlay가 적용한다. 제품 이름을 바꿔도 프로필·등록 식별자는 바꾸지 않는다.
Windows 패키징은 설치·제거를 Chromium에 맡기고 배포 파일·공통 릴리즈 메타데이터만 소유한다.
`branding/VERSION`이 제품의 네 자리 배포 버전을 소유한다. 매 배포마다 이전 버전보다
큰 값으로 올린다. 엔진의 major/minor/build는 그대로 유지하고 마지막 patch를 엔진 이상으로
정한다. 두 플랫폼의 브랜딩 적용 진입점에서 검증·반영하며, 엔진 checkout의 원본 버전과
호환되지 않는 값은 빌드 전에 거부한다. 설치·실행 파일 버전이 다르면 패키징도 거부한다.

macOS·Linux 지원 시 같은 제품 식별자에 각 플랫폼의 검증된 bundle/desktop·데이터·서명 설정과
패키징 진입점을 추가한다. Windows 레지스트리나 설치 명령을 공용 제품 설정에 섞지 않는다.
현재 체크포인트는 macOS·Linux 설치·프로필을 변경하거나 검증하지 않는다.
Windows 시스템 전체 설치·서비스·앱 자동 업데이트도 이 테스트판의 범위 밖이다.

## Windows 검증 기록

2026-10-25 Windows x64의 실제 unsigned component 설치 파일로 다음을 확인했다.
전체 앱·설치 파일·native 설치 테스트가 빌드됐고, 설치된 버전 폴더의 필터·실행 리소스·
고지·원본 묶음 9개가 패키지 메타데이터의 SHA-256과 모두 일치했다.

- 별도 `--user-data-dir` 없이 실행해 native 버전 화면이
  `%LOCALAPPDATA%\Yee\User Data\Default`를 보고했다. 정상 페이지의 본문과 캡처를 확인했다.
- 같은 버전 수리와 제거 후 재설치 뒤에도 동일한 웹 저장 데이터가 유지됐다.
  수리의 native 상태 1과 성공 종료코드 0을 함께 확인했다.
- 일반 제거는 프로필을 보존했고, 명시적 데이터 삭제 제거는 시험 프로필을 삭제했다.
  마지막에는 설치 실행 파일·제거 항목과 시험 루트가 남지 않았다.
- 설치·수리·최종 제거 뒤에 기존 Chrome/Chromium·공유 실행 파일 등록·확장자·RLZ와
  기본 브라우저 설정의 hash가 시험 시작 전과 일치했다.
- 설치본의 Windows rendering fixture는 켬·끔·사이트 예외 세 모드를 통과했다.
  광고 요청 미도달·iframe/이미지 접기·상속 CSS/scriptlet·정상 콘텐츠 복구를 확인했다.

`install_static_unittests` 56개와 `setup_unittests` 297개 검사에서 실패가 없었다.
후자의 시스템 설치 미지원·관리자 서비스 권한이 필요한 시험은 지원 조건에 따라 skip했다.
tooling은 118개 중 macOS 전용 등 40개를 skip하고 나머지를 통과했다.
native 패치 역적용·범위 내 공백 검사와 JavaScript·PowerShell 구문 검사도 통과했다.

원시 결과는 로컬 `.local-build/windows-install-test-n8J1ZT/`와 설치본 rendering 결과에 있다.
초기 진단 회차의 게시자 문자열 전체 오인·문서 전환 중 context 소멸·버전 화면의 빈 초기
필드는 시험 도구에서 수정했다. 최종 완료 결과는 위 전체 흐름을 통과한 회차만 사용한다.
이 검증은 현재 개발 PC 범위다. 다른 깨끗한 PC, 시스템 전체 설치, 서명·정식 배포,
macOS·Linux 실행을 검증한 것으로 확대하지 않는다.

## Windows 업데이트 검증 기록

2026-10-25 실제 사용자의 설치본 `153.0.8005.0`에서 새 설치 파일 `153.0.8005.1`을
실행해 업데이트 성공 상태 2·프로세스 종료 0을 확인했다. 기존 설치나 프로필을 제거하지
않았다. 기본 프로필의 웹 저장 데이터·선택한 영속 설정을 비교했고, 별도 시험 프로필의
비어 있지 않은 북마크를 실제 API로 생성·조회해 홈·시작 설정·광고 차단 예외와 함께
업데이트 뒤 유지됨을 확인했다. Windows 앱 목록·실행 파일·설치 등록과 9개 payload도
새 버전과 일치했다. 과거 설치 파일은 종료 4로 거부됐고 최신 실행 파일 hash가 유지됐다.
같은 버전 수리는 성공했으며 기존 Chrome·Chromium 등록과 기본 브라우저도 유지됐다.

최초 연속 검사는 위 단계를 통과한 뒤 광고 차단 모드 전환에서 종료 중인 보조 프로세스
2개를 감지해 중단됐다. 검사 도구에 정상 종료 후 전체 프로세스가 끝날 때까지의 제한된
대기를 추가했다. 수정 후 설치본 광고 차단의 켬·끔·사이트 예외 세 모드를 별도로 다시
통과했다. 전체 업데이트를 재실행한 결과로 합치지 않는다. 실제 설치본은 새 버전으로 남겼다.

tooling 122개 중 플랫폼 전용 등 40개를 skip하고 나머지를 통과했고, 종료 대기의 지연·
종료 실패·조회 오류를 포함한 런타임 시험도 통과했다. 독립 검수와 수정 후 재검수에서
수정할 발견 사항은 없었다. 업데이트 증거는 `.local-build/windows-install-test-PkOcFb/`,
수정 후 광고 차단 증거는 `.local-build/rendering-e2mHtu/`에 따로 보관한다.

빌드 당시 작업 중인 변경이 있어 `release.json`의 `working_tree_dirty`는 `true`다.
위 기준 커밋만으로 같은 산출물을 재현할 수 있다고 주장하지 않는다.
`chrome.exe`·`chrome.dll`·`setup.exe`·`mini_installer.exe`의 제품 버전은 모두
`153.0.8005.4`이며, 설치 파일 해시와 필터·실행 리소스·고지·원본 묶음 9개의
해시가 메타데이터와 일치했다. 설치된 `chrome.dll`도 최종 빌드와 일치했다.

검증 시작 시 기본 프로필에 열려 있던 기존 그룹은 0개였다. 실제 기본 프로필의
한 창에 검증용 그룹 두 개와 HTTP 탭 네 개를 만들었다. 파란 그룹은 펼치고 녹색
그룹은 접은 상태로, 그룹 이름·색상·접힘·그룹 순서·멤버 탭 순서를 비교했다.
작업표시줄에 이미 고정된 `Yee.lnk`를 사용했으며 고정 해제·다시 고정을 하지 않았다.

### 153.0.8005.3에서 새 버전으로 업데이트

설치 프로세스 종료 0과 새 버전 적용, 기존 바로가기의 대상·인수·아이콘 경로·앱
식별자, Windows Shell이 읽은 정규화 아이콘 픽셀의 보존을 확인했다. 기존 아이콘으로
실행한 새 세션의 그룹 구성은 재설치 전과 일치했다.

이후 검증용 탭 정리 단계에서 정상 종료 대기가 초과돼 최초 드라이버는 종료 1로
실패했다. 설치·보존 assertion이 끝났더라도 이 회차 전체를 통과로 기록하지 않는다.
검증용 제어 연결이 있는 창에는 `Browser.close` 정상 종료를 먼저 요청하도록 도구를
보완했다. 별도 정리 복구의 첫 시도도 검증용 그룹의 펼침 상태 차이로 중단됐다.
복구에서는 검증용 그룹의 접힘 차이만 허용하고 기존 그룹과 나머지 상태를 비교한 뒤,
기록된 검증 URL 네 개만 정리했다. 원본 그룹 상태로 복귀하고 기존 아이콘으로 새
설치본을 실행한 최종 확인은 통과했다. 복구 실행을 그룹 보존의 추가 근거나 최초
업데이트 전체 흐름을 다시 통과한 결과로 합치지 않는다. 강제 종료는 사용하지 않았다.

### 153.0.8005.4 동일 버전 재설치

보완한 절차로 그룹 두 개·탭 네 개를 다시 만든 뒤 같은 설치 파일을 실행했다.
설치 프로세스와 전체 검증 드라이버가 모두 종료 0으로 끝났고, 정리 뒤 최종 상태
검사도 통과했다. 설치 직후와 기존 아이콘 실행 후에 바로가기 정보·고정 상태·아이콘
픽셀이 유지됐다. 새 native 세션에서 그룹 메타데이터·멤버 수를, 실제 그룹 API에서
그룹 구성·순서를 비교해 일치를 확인했다.

원래 바로가기 실행에는 `--restore-last-session`·`--remote-debugging-port`·
`--user-data-dir`를 추가하지 않았다. 최종 정리 후 기존 아이콘으로 실행한 프로세스에서
`153.0.8005.4\chrome.dll` 로드를 확인했고 설치된 DLL의 해시는 다음과 같았다.

`B4C145F02624474D465B1F20C7E4459FAC43A4AB1A0E04439DBC78CDE1EFBCB7`

검증 URL만 정리한 뒤 그룹 상태가 원본과 같음을 확인했고, 기존 아이콘으로 새
설치본을 열어뒀다. 이 기록은 현재 개발 PC의 사용자별 설치 범위이며, 다른 PC나
macOS·Linux 검증을 의미하지 않는다.
