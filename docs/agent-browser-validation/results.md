# Yee Agent 검증 결과

이 문서는 현재 사람이 읽을 결과 요약이다. 기계 판독 수치와 48개 쌍별 기록은
[`comparison.json`](comparison.json), 원본 위치와 해시는
[`evidence-index.json`](evidence-index.json)을 따른다.

## 현재 판정

고정 범위는 원래 12개 시나리오를 fresh ACP·지속 세션과 fixture seed 11·29로
조합한 48개다. Grok 4.6/high, 1,440×900@1, 모델 재시도 0 조건을 유지했다.
사람이 응답한 승인·선택·인증 대기는 비교 시간에서 0초로 통제하고 횟수와 실패
비용은 보존했다.

| 표본 | 통과 | 대기 제외 시간 | 실제 총 토큰 | 모델 호출 | MCP 호출 / 오류 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 현재 Yee | 48/48 | 2,314.930초 | 4,483,169 | 226 | 152 / 0 |
| 재사용한 Aside | 36/48 | 3,708.277초 | 11,930,211 | 463 | 375 / 19 |

실패 비용을 포함한 전체 합계에서 Yee는 Aside보다 시간이 37.57%, 토큰이 62.42%,
모델 호출이 51.19% 적었다. 직전 Yee 체크포인트 46/48, 2,386.330초,
5,201,651토큰, 238호출과 비교해 통과는 2건 늘고 시간은 2.99%, 토큰은 13.81%,
호출은 5.04% 줄었다. 정확성과 시간·토큰 동시 개선 목표를 현재 표본에서 달성했다.

48개 쌍을 개별 비교하면 Yee가 42개에서 더 빨랐고 47개에서 토큰을 덜 썼으며,
46개에서 모델 호출이 더 적었다. 차이가 큰 시간 예외는 fresh seed29 S04
(+90.629초), persistent seed11 S01(+27.495초), fresh seed29 S05(+26.571초)다.
세 사례는 모델 API 시간이 각각 143.381초/5호출, 85.139초/4호출,
66.564초/6호출로 길었지만 토큰과 호출은 Aside보다 적었다. persistent seed29 S05와
persistent seed11 S03은 +2.709초, +2.311초의 단일 표본 차이다. fresh seed11 S03은
+12.180초였으나 Aside가 정답 gate를 통과하지 않아 동일 성공 비교에서 제외한다.

토큰이 더 많았던 유일한 쌍은 fresh seed11 S05다. Yee가 불필요한 탭 목록 조회와
분리된 대기·스크롤을 포함해 Aside보다 모델 호출을 2회 더 사용하면서 22,482토큰이
늘었고, 시간은 3.621초 짧았다. 이 한 건 때문에 모든 개별 시나리오에서 우위라고
말할 수는 없지만 전체 정확도와 합계 효율 우위는 확인됐다.

## 이번에 확정한 변경

지속 실행기가 이전 작업의 연결 해제를 다음 작업의 reload에 의존해 늦게 도착한
중단 신호가 새 작업 권한까지 해제할 수 있었다. 각 Yee 작업 종료 시 `detach`를
명시적으로 실행하고 승인된 탭 목록이 비었는지 확인한 뒤 다음 작업으로 넘어가도록
고쳤다. S01~S05를 모델 호출 0회로 연결 경계만 검사한 preflight가 5/5를 통과했고,
그 뒤 persistent seed11과 seed29가 각각 12/12를 통과했다. 지속 JavaScript REPL에는
`var` 또는 고유 식별자를 사용하라는 범용 안내도 추가해 이전 작업 선언과의 충돌을
막았다.

외부 변경이나 문서 교체 직후 첫 관찰이 잘못된 delta로 전달되던 baseline 보정과
구조화된 Native 승인 카드는 유지한다. 승인 카드는 Agent 식별, 요청 제목, origin,
작업 상세, 안전 안내, 명확한 동작 버튼과 질문 입력을 구분하며 기본 선택은 취소다.
브리지 계약 검사와 실제 앱의 중앙 배치·무크래시 렌더링은 통과했다. Computer Use가
별도 Native 자식 모달을 주 창 이미지에 포함하지 않아 light/dark, 긴 요청, 질문
입력과 키보드·접근성 상태의 픽셀 증거는 아직 남아 있다.

## 표본과 비용 처리

fresh 결과는 사용자 조작과 실행기 중단 뒤 보존된 원본 실행들에서 시나리오별
유효 행을 명시적으로 고른 composite다. 각 행의 원본 경로와 ACP span SHA-256을
비교 JSON에 남겼다. persistent 두 조건은 각각 한 세션·한 브라우저 프로세스에서
12개를 연속 수행했다. 실행기와 preflight를 다듬는 동안 발생한 31개 모델 요약,
781,249토큰, 65호출, 854.335 모델초는 채택 표본에 섞지 않고 별도 개발 비용으로
보존했다.

Yee는 Native 승인 60회와 사용자 handoff 8회를 기록했다. Aside는 host 입력·인증
8회와 문서 승인 4회가 확인되지만 Native 승인 전체 횟수는 원본 계측에 없어 미확인
상태를 유지한다. 시간 비교에서는 양쪽 모두 실제 사용자 대기만 0초로 처리했다.

Aside의 모델, fixture, seed, viewport, 승인 정책과 세션 조건은 바뀌지 않아 기존
48개 baseline을 재사용했다. 현재 공통 프롬프트는 458바이트 짧고 사용자가 최종
운영 비교에서 무시 가능한 차이로 승인했다. 같은 현재 프롬프트를 쓴 seed83
S07~S09 세 쌍은 모두 Yee가 시간과 토큰에서 앞섰다. 이 조건 차이와 단일 표본
변동성은 비교 JSON에 그대로 남긴다.

## 남길 교훈과 한계

- 최신 판정은 비교 JSON 하나에서 파생하고 Markdown에는 해석만 중복한다.
- Yee만 변경되고 비교 조건이 같으면 Aside 전체 시험을 반복하지 않는다. 조건이
  달라진 부분만 보완하고 재사용 근거와 원본 해시를 남긴다.
- 실행기 실패와 제품 실패를 구분하며, 실패·중단·재시도 비용과 원본 응답을 버리지
  않는다. 관찰 시간 초과만으로 프로세스 종료를 판단하지 않는다.
- 작업 경계에서는 이전 capability 해제를 명시적으로 증명한다. 다음 화면 전환이
  이전 작업 정리를 대신하게 두지 않는다.
- 시나리오 ID·seed·정답 값 분기 대신 capability, schema, 완료 receipt와 기준 상태를
  개선한다. 정답 기준과 안전 조건은 성능을 위해 약화하지 않는다.

조건별 채택 표본은 각 1개이므로 시나리오별 지연 분산, 모든 사이트와 모든 모델의
우위를 증명하지 않는다. provider 내부 재시도와 실제 hard turn cap, Aside Native
승인 전체 횟수는 관측되지 않았다. Luna/Kimi 결과는 호환성 근거이며 Grok/Aside
합계에 섞지 않는다.
